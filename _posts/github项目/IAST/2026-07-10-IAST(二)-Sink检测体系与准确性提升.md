# IAST(二)-Sink 检测体系与准确性提升

本篇在全景中的角色：上一篇实现了四类插桩点的最小闭环，但只有命令注入一种 Sink。本篇要解决的核心矛盾是——Sink 不全是具体类，接口/抽象类/构造函数怎么检测？围绕这个矛盾，本篇分五个部分展开：三种 JVM 关系检测模式（一）、Sink 全覆盖（二）、净化器（Sanitizer）体系（三）、漏洞去重（四）、JSON 规则驱动（五）。

***

## 一、Sink 检测的三种 JVM 关系模式

上一篇的命令注入 Sink 是 `Runtime.exec`——一个具体类上的具体方法，直接匹配即可。但真实业务里的 Sink 远不止这一种：SQL 注入的 `Statement`（数据库语句接口）`executeQuery` 是接口方法，SSRF 的 `HttpURLConnection`（HTTP URL 连接抽象类）`connect` 是抽象类方法，Path Traversal 的 `FileInputStream`（文件输入流）`<init>` 是构造函数。这三种 Sink 在 JVM（Java虚拟机）字节码层面体现为不同的继承关系，检测方式也不同。

| 检测模式 | 目标类型 | JVM 关系 | 字节码检测字段 | 典型 Sink |
| :--- | :--- | :--- | :--- | :--- |
| 接口实现 | 接口 | implements | `interfaces` + 方法扫描 | `Statement.executeQuery` |
| 抽象类子类 | 抽象类 | extends | `superName` | `HttpURLConnection.connect` |
| 具体类构造函数 | 具体类 | 直接匹配 | `className` 精确 + `<init>` | `FileInputStream.<init>(String)` |

接口和抽象类无法直接调用 `retransformClasses`（类重转换），只能在每个类加载回调里动态检测其实现/子类；具体类可以直接匹配，但构造函数这类特殊方法需要额外描述符约束。下面三节分别讲三种模式的实现。

### 1.1 接口实现模式：interfaces 数组与方法扫描

SQL 注入的 Sink 是 `java.sql.Statement` 接口的 `executeQuery(String)` 方法。无论原生 JDBC、MyBatis 还是 Hibernate，底层最终都经过这个接口。但 `Statement` 是接口，没有方法体，`retransformClasses` 无法操作。真正要拦截的是它的具体实现类——H2 的 `JdbcStatement`、MySQL 的 `StatementImpl` 等。不同驱动的实现类名不同，无法硬编码匹配，但所有实现类有一个共同特征：包含 `executeQuery(String)` 方法。

`isStatementClass` 的作用是在 `ClassFileTransformer`（类文件转换器）`transform()` 回调里判断当前类是否为 Statement 的实现类。检查三个条件：不是接口本身、不是抽象类、含 `executeQuery(String)` 方法：

```java
public static boolean isStatementClass(String className, byte[] classfileBuffer) {
    if ("java/sql/Statement".equals(className)) return false;
    ClassReader cr = new ClassReader(classfileBuffer);
    if ((cr.getAccess() & Opcodes.ACC_INTERFACE) != 0) return false;
    if ((cr.getAccess() & Opcodes.ACC_ABSTRACT) != 0) return false;
    // 扫描方法列表,找 executeQuery(String)
}
```

H2 的 `JdbcStatement` 在首次 SQL 请求时被加载，立刻被检测并插桩——不依赖特定 JDBC 驱动，无需预配置。

找到实现类后还要匹配方法描述符。`executeQuery(String)` 的描述符是 `(Ljava/lang/String;)Ljava/sql/ResultSet;`，`execute(String)` 是 `(Ljava/lang/String;)Z`，`executeUpdate(String)` 是 `(Ljava/lang/String;)I`。三个方法参数部分相同、返回类型不同。用 `startsWith("(Ljava/lang/String;)")` 前缀匹配，一条规则覆盖三个方法——只要第一个参数是 String，无论返回什么类型。

**PreparedStatement（预编译语句接口）为何不报漏洞**：PreparedStatement 的 `executeQuery` 也是 String 参数，但不报漏洞的原因在于污点传播路径而非描述符匹配。参数化查询中，SQL 模板 `SELECT * FROM users WHERE id = ?` 本身不含污点；用户输入通过 `setString(1, input)` 单独绑定，污点到达 setString 而非 executeQuery。之后调用的是无参 `executeQuery()`，没有字符串参数，因此不触发 Sink。参数化查询不报漏洞的原因是污点未到达 Sink 方法，而非跳过了检查。

### 1.2 抽象类子类模式：superName 字段检测

SSRF 的 Sink 是 `HttpURLConnection.connect()`，但 `java.net.HttpURLConnection` 是抽象类。抽象类的子类通过 extends 继承，在字节码中体现为 `superName` 字段；接口的实现类通过 implements 实现，体现为 `interfaces` 数组。两种 JVM 继承关系的检测方式不同——接口检查 `interfaces` 数组，抽象类检查 `superName` 字段。

`isHttpUrlConnectionClass` 的作用是判断当前类是否为 HttpURLConnection 的具体子类。读取字节码，检查直接父类 `superName` 是否为 `java/net/HttpURLConnection`：

```java
public static boolean isHttpUrlConnectionClass(String className, byte[] classfileBuffer) {
    if ("java/net/HttpURLConnection".equals(className)) return false;
    ClassReader cr = new ClassReader(classfileBuffer);
    if ((cr.getAccess() & Opcodes.ACC_INTERFACE) != 0) return false;
    if ((cr.getAccess() & Opcodes.ACC_ABSTRACT) != 0) return false;
    return "java/net/HttpURLConnection".equals(cr.getSuperName());
}
```

与 Statement 的检测逻辑相比，核心差异在最后一步：Statement 用方法列表扫描确认"这个类实现了什么行为"（行为特征匹配），HttpURLConnection 用 `superName` 确认"这个类继承了谁"（血统特征匹配）。

Sink Handler 也有差异。SQL 注入的 `executeQuery(String sql)` 有参数，污点直接在参数里。SSRF 的 `connect()` 没有参数，污点信息在 HttpURLConnection 对象内部，需要通过反射获取 URL：

```java
public static void onHttpUrlConnectEnter(Object connection) {
    try {
        Method getURLMethod = connection.getClass().getMethod("getURL");
        Object url = getURLMethod.invoke(connection);
        String urlStr = url.toString();
        checkAndReport(urlStr, "HttpURLConnection.connect", "SSRF");
    } catch (Exception e) {
        // 回退:子串级污点检查 connection.toString()
    }
}
```

插桩仅需传入 this（HttpURLConnection 实例），Handler 内部反射取 URL 做污点判断。

### 1.3 具体类构造函数模式：className 精确匹配

Path Traversal 的 Sink 是 `new FileInputStream(path)`——构造函数 `<init>`。`FileInputStream` 是具体类，可以直接用 `className` 精确匹配，不需要像接口/抽象类那样动态检测子类。

构造函数在字节码层面和普通方法有几处不同：普通方法用 ARETURN（返回对象引用）退出，构造函数用 RETURN（void 返回）退出；普通方法的 slot 0 是已初始化的 this，构造函数的 slot 0 也是 this，但在执行 `<init>` 之前 this 尚未初始化。这些差异决定插桩只能在入口做——EXIT 时 RETURN 的语义和 ARETURN 不同，不适合出口插桩。

`FileInputStreamCtorMethodVisitor` 的作用是在构造函数入口注入插桩代码，加载 this + path 参数传给 Handler：

```java
static class FileInputStreamCtorMethodVisitor extends MethodVisitor {
    @Override
    public void visitCode() {
        super.visitCode();
        mv.visitVarInsn(Opcodes.ALOAD, 0);  // this (FileInputStream)
        mv.visitVarInsn(Opcodes.ALOAD, 1);  // path (String)
        mv.visitMethodInsn(Opcodes.INVOKESTATIC, HANDLER_CLASS,
                "onFileInputStreamCtorEnter",
                "(Ljava/lang/Object;Ljava/lang/Object;)V", false);
    }
}
```

Handler 直接检查 path 参数：

```java
public static void onFileInputStreamCtorEnter(Object fis, Object path) {
    String pathStr = (path instanceof String) ? (String) path : path.toString();
    checkAndReport(pathStr, "FileInputStream.<init>", "PathTraversal");
}
```

**路由安全**：`FileInputStreamCtorMethodVisitor` 的匹配条件是 `<init> + (Ljava/lang/String;)V`——任何 String 参数的构造函数都会匹配。但 `IastTransformer` 只对 `isTargetClass` 匹配的类路由到 SinkTransformer，而 `isTargetClass` 仅匹配 `java/io/FileInputStream`，其他类的 String 构造函数不会命中这里。路由层做类过滤，方法匹配条件做方法过滤，两层条件配合保证不误插。

### 1.4 三种模式的对比

接口实现基于"行为"——`interfaces` 数组里有没有目标方法签名；抽象类子类基于"血统"——`superName` 是不是目标抽象类；具体类构造函数基于"身份"——`className` 精确匹配加 `<init>` 描述符约束。三种 JVM 继承关系在字节码中体现为不同字段，检测方式也因此不同。这三种模式覆盖了 Java 安全 Sink 的主要形态，后续新增 Sink 类型都归入这三种之一。

## 二、Sink 全覆盖：十类漏洞的 86 条规则

基于三种检测模式，Sink 规则从初版的 1 条扩展到 86 条，覆盖 10 类漏洞。本节按漏洞类型梳理覆盖情况，重点讲 XSS 和 Path Traversal 的扩展细节。

### 2.1 XSS Sink 全覆盖

XSS 的 Sink 是输出方法：`PrintWriter` 和 `JspWriter` 的所有写方法。初版仅 hook `PrintWriter.print(String)`，覆盖严重不足。系统性补全后覆盖以下方法：

| 类 | 方法 | 参数类型 | Handler |
| :--- | :--- | :--- | :--- |
| `PrintWriter` | `print` / `write` / `println` | `String` | `onPrintWriterPrintEnter` |
| `PrintWriter` | `write` | `String, int, int` | `onPrintWriterPrintEnter` |
| `PrintWriter` | `format` / `printf` | `String, Object[]` | `onPrintWriterFormatEnter` |
| `PrintWriter` | `format` / `printf` | `Locale, String, Object[]` | `onPrintWriterFormatLocaleEnter` |
| `PrintWriter` | `print` / `write` / `println` | `char[]` | `onPrintWriterCharArrayEnter` |
| `PrintWriter` | `write` | `char[], int, int` | `onPrintWriterCharArrayEnter` |
| `JspWriter` | `print` / `write` | `String` | `onJspWriterPrintEnter` |
| `JspWriter` | `print` / `write` / `println` | `char[]` | `onJspWriterCharArrayEnter` |
| `JspWriter` | `write` | `char[], int, int` | `onJspWriterCharArrayEnter` |

**CoyoteWriter 子类动态识别**：Tomcat 的 `CoyoteWriter` 继承自 `PrintWriter`，覆写了 `write` / `println` 等方法。如果只插桩 `PrintWriter` 本身，`CoyoteWriter` 覆写的方法不会被拦截。`isPrintWriterClass()` 通过检查 `superName` 动态识别 `PrintWriter` 子类，在 `IastTransformer` 中路由到 `SinkTransformer`。这和 HttpURLConnection 的检测逻辑同属"抽象类子类模式"的变体——PrintWriter 不是抽象类，但其子类同样需要动态识别。

**char[] 参数支持**：部分 Benchmark 用例通过 `String.toCharArray()` 将污点字符串转为 `char[]` 再输出。如果不覆盖 `char[]` 类型的 Sink 方法，污点在 `toCharArray()` 后断裂，Sink 检测失效。这要求同时在传播器（Propagator）中补充 `String.toCharArray()` 的传播规则。

### 2.2 Path Traversal Sink 扩展

Path Traversal 的 Sink 是文件访问类的构造函数与路径操作方法。初版只覆盖 `FileInputStream`，扩展后覆盖 7 个类：

| 类 | 构造函数签名 | 漏洞类型 |
| :--- | :--- | :--- |
| `FileInputStream` | `<init>(String)` / `<init>(File)` | Path Traversal |
| `FileOutputStream` | `<init>(String)` / `<init>(String, boolean)` / `<init>(File)` / `<init>(File, boolean)` | Path Traversal |
| `FileReader` | `<init>(String)` / `<init>(File)` | Path Traversal |
| `FileWriter` | `<init>(String)` / `<init>(String, boolean)` / `<init>(File)` / `<init>(File, boolean)` | Path Traversal |
| `Scanner` | `<init>(File)` / `<init>(String)` | Path Traversal |
| `Files` (NIO) | `newInputStream(Path)` / `readAllBytes(Path)` / `write(Path, byte[])` | Path Traversal |
| `File` | `<init>(File, String)` / `<init>(String, String)` | Path Traversal |

**构造函数描述符前缀匹配**：`FileOutputStream` 和 `FileWriter` 有多种重载（带 `boolean append` 参数），使用 `descriptor.startsWith("(Ljava/lang/String;")` 和 `descriptor.endsWith(")V")` 组合匹配，一条规则覆盖多个重载。这和 Statement 的 `startsWith` 前缀匹配思路一致，但适用对象从接口方法变为构造函数。

## 三、净化器（Sanitizer）：消除污点降低误报

上一版的引擎只实现了四类插桩点（HTTP、SOURCE、PROPAGATOR、SINK），污点只能被添加和传播，没有任何机制能删除污点。所以只要污点到达 Sink 就报漏洞，无论中间经过了什么操作。这是误报的主要来源之一。

### 3.1 净化器（Sanitizer）的定义与作用

**净化器（Sanitizer）** 的作用是显式消除已有污点标记，使该数据后续传播不再触发 Sink 告警。Sanitizer 是污点追踪体系中的第五类插桩点，与 SOURCE/PROPAGATOR/SINK 配合，构成"标记-传播-净化-检测"完整闭环。

`Integer.parseInt(id)` 是典型例子。无论用户输入什么，能成功 parseInt 的就一定是合法整数，含非法字符的输入会抛 NumberFormatException 直接报错，不会到达 Sink。所以 parseInt 之后的返回值无法构造注入。但上一版不知道这一点——污点标记在原始的 String 对象上，无法被删除，后续这个字符串变量如果又被拼进 SQL，污点照样传播到 Sink，报 SqlInjection。这就是误报。

新增 Sanitizer 插桩后，在 `parseInt` / `parseLong` 的出口回调中调用 `TaintContext.removeTaint(input)` 把原始字符串上的污点标记删掉。这样后续即使这个字符串被拼接，也不会传播污点：

```java
private static void sanitize(Object input, String sanitizerMethod) {
    if (input == null) return;
    if (TaintContext.isTainted(input)) {
        TaintContext.removeTaint(input);
    }
}
```

### 3.2 基本类型返回值的装箱处理

出口插桩有一个字节码层面的关键问题。`parseInt` 返回 int 基本类型，而 Handler 的参数声明为 Object。JVM 不允许直接把 int 当 Object 传——int 是基本类型，Object 是引用类型，两者在栈上的表示不同。处理方式是在 IRETURN（int 返回指令）之前插入装箱指令，调用 `Integer.valueOf(int)` 把 int 装箱为 Integer 对象再传递给 Handler。

装箱之前还需要一条 DUP 指令。DUP 的意思是"复制栈顶值"——IRETURN 本身也需要栈顶的 int 作为返回值，如果装箱时直接把 int 弹出传给 Handler，原来的返回值就丢失了。DUP 之后栈顶有两个 int，一个拿去装箱、传给 Handler，另一个留在栈上给 IRETURN 正常返回：

```java
if (opcode == Opcodes.IRETURN) {
    mv.visitVarInsn(Opcodes.ALOAD, 0);           // 加载 input
    mv.visitInsn(Opcodes.DUP);                    // DUP int 返回值
    mv.visitMethodInsn(Opcodes.INVOKESTATIC,
            "java/lang/Integer", "valueOf",
            "(I)Ljava/lang/Integer;", false);     // int → Integer
    mv.visitMethodInsn(Opcodes.INVOKESTATIC,
            HANDLER_CLASS, "onParseIntExit",
            "(Ljava/lang/Object;Ljava/lang/Object;)V", false);
}
```

栈序列：`[..., int_result]` → ALOAD 0 加载 input → `[..., int_result, input]` → DUP 复制栈顶 int → `[..., int_result, input, int_result]` → valueOf 装箱 → `[..., int_result, input, Integer_object]` → Handler 消费两个参数 → `[..., int_result]` → IRETURN。

`Long.parseLong` 类似，但 long 占 2 个栈位（JVM 里 long 和 double 是 64 位，占两个 slot），需要 `DUP2`（复制栈顶的两个 slot）而不是 DUP。

五类插桩点至此完整：

| 类型 | 作用 | 方向 |
| :--- | :--- | :--- |
| HTTP | 请求边界 | 开关（生命周期） |
| SOURCE | 标记污点 | 写入 |
| PROPAGATOR | 传播污点 | 读 → 写 |
| SANITIZER | 消除污点 | 删除 |
| SINK | 检测污点 | 只读 → 报告 |

### 3.3 PreparedStatement.setString：参数化查询的净化

真实业务中最常见的净化是 PreparedStatement 的参数化查询：

```java
// 直接拼接 → SQL 注入(危险)
stmt.executeQuery("SELECT * FROM users WHERE name = '" + name + "'");

// 参数化查询 → 安全(setString 把 name 作为数据绑定,不参与 SQL 解析)
PreparedStatement pstmt = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
pstmt.setString(1, name);  // name 是污点,但参数化后不再是注入风险
pstmt.executeQuery();
```

`setString` 把用户输入作为数据绑定到占位符，而不是拼进 SQL 语句。绑定的数据不会被 SQL 解析器解释为 SQL 语法，所以不可能构造注入。在 `setString` 的出口插桩做 Sanitizer，把传入的 value 参数上的污点删掉。

和 Statement Sink 一样，PreparedStatement 也是接口，需要扫描字节码检测 `setString(ILjava/lang/String;)` 方法来判断实现类。`setString` 的出口插桩也有细节：它是 void 方法，返回指令是 RETURN（void 返回），插桩在 RETURN 之前加载 this 和 value 参数：

```java
if (opcode == Opcodes.RETURN) {
    mv.visitVarInsn(Opcodes.ALOAD, 0);  // this (PreparedStatement)
    mv.visitVarInsn(Opcodes.ALOAD, 2);  // value (slot 0=this, 1=int index, 2=String value)
    mv.visitMethodInsn(Opcodes.INVOKESTATIC, HANDLER_CLASS,
            "onSetStringExit", "(Ljava/lang/Object;Ljava/lang/Object;)V", false);
}
```

注意 ALOAD 2 而不是 ALOAD 1。ALOAD 是"从局部变量表加载对象引用到栈顶"的指令，后面的数字是 slot 编号。`setString` 的参数槽位是：slot 0=this，slot 1=int index（int 占 1 个 slot），slot 2=String value。要净化的是 value，所以加载 slot 2。

### 3.4 Sanitizer 体系：19 条规则覆盖五类净化

从单一的 parseInt 扩展到 19 条 Sanitizer 规则，覆盖 SQL/CMDI/XSS 三类漏洞的净化场景：

| 漏洞类型 | 净化方法 | 类 | 作用 |
| :--- | :--- | :--- | :--- |
| SqlInjection | `setString` / `setObject` | `PreparedStatement` | 预编译参数化查询 |
| SqlInjection | `setInt` / `setLong` / `setFloat` / `setDouble` / `setShort` / `setByte` / `setBoolean` / `setBigDecimal` / `setDate` / `setTimestamp` | `PreparedStatement` | 基本类型参数绑定 |
| SqlInjection | `encodeForSQL` | ESAPI Encoder（通配） | ESAPI SQL 编码 |
| CommandInjection | `encodeForOS` | ESAPI Encoder（通配） | ESAPI 操作系统命令编码 |
| XSS | `htmlEscape` | `HtmlUtils`（Spring） | HTML 实体编码 |
| XSS | `escapeHtml` | `StringEscapeUtils`（Apache Commons） | HTML 实体编码 |
| XSS | `encodeForHTML` / `encodeForJavaScript` | ESAPI Encoder（通配） | ESAPI XSS 编码 |
| XSS | `encode` | `URLEncoder` | URL 编码 |

**通配规则**：ESAPI Encoder 的类名不固定（可能是 `org.owasp.esapi.reference.DefaultEncoder` 或其他实现），使用 `className: "*"` + `methodName: "encodeForSQL"` 通配匹配，只要方法名匹配即插桩。

### 3.5 路由优先级与身份冲突

**身份冲突（Identity Conflict）** 指同一个类同时具备多种身份（如同时是 Sanitizer 容器和 Sink 容器），路由层只能命中一条路径，需要通过优先级决定命中哪条。`JdbcPreparedStatement` 同时含 `setString`（Sanitizer）和 `executeQuery`（Sink）。一个类可以同时满足多个路由条件，但路由只命中第一个匹配——如果 Statement Sink 在前，PreparedStatement 的 `setString` 净化就不会被应用。

所以 PreparedStatement Sanitizer 的路由必须排在 Statement Sink 之前：

```
路由顺序(关键部分):
1. PreparedStatement Sanitizer(含 setString → 净化 + Sink 插桩)
2. Statement Sink(含 executeQuery → 仅 Sink 插桩)
```

PreparedStatement 实现类（如 H2 的 `JdbcPreparedStatement`）命中 Sanitizer 路由后，`executeQuery` 不会被插桩——SanitizerTransformer 的 ClassVisitor 只处理 `setString`，其他方法原样通过。这没问题：PreparedStatement 的 `executeQuery()` 不接收 SQL 字符串参数（SQL 在 `prepareStatement(sql)` 时已固定），`setString` 的参数通过参数化绑定，不会被解释为 SQL 的一部分。所以 PreparedStatement 的 executeQuery 不需要 Sink 插桩——这正是参数化查询的设计原理：数据与 SQL 结构分离，污点在 setString 处被净化，executeQuery 不再触发。

普通 Statement 实现类不含 `setString`，命中第二个路由——Statement Sink，只插桩 executeQuery。这就是身份冲突的解决方式：同一个类同时具有两种身份，路由优先级决定它命中哪条路径，而那条路径覆盖了它真正需要的行为。

***

## 四、漏洞去重：三元组键控的请求内合并

**漏洞去重（Vulnerability Deduplication）** 指同一请求生命周期内，对相同三元组的重复触发只报一次，避免循环调用等场景下产生大量重复告警。同一请求中同一个 Sink 方法被多次调用（如循环里多次 `stmt.executeQuery(sql)`），三元组完全相同时会重复报漏洞。

`VulnReportCollector.addReport()` 的作用是在添加报告前遍历已有报告，比较去重键。去重键是 `vulnType + source + sinkMethod` 三元组：

```java
private static boolean sameKey(VulnerabilityReport a, VulnerabilityReport b) {
    return eq(a.getVulnType(), b.getVulnType())
            && eq(a.getSource(), b.getSource())
            && eq(a.getSinkMethod(), b.getSinkMethod());
}
```

| 场景 | 去重键 | 效果 |
| :--- | :--- | :--- |
| Runtime.exec + ProcessBuilder.start 同一命令注入 | sinkMethod 不同（`Runtime.exec` vs `ProcessBuilder.start`） | 两条都保留（不同 Sink 入口算不同漏洞） |
| 同一请求两次 `stmt.executeQuery(sql)` | 三元组完全相同 | 第二条跳过 |

去重只在同一请求生命周期内生效：Http Handler 的 `leaveRequest()` 调用 `VulnReportCollector.clear()`，请求结束自动清空。

## 五、JSON 规则驱动：Hook 规则与代码解耦

前面的章节展示了 Sink 规则怎么从一条变成多条，Sanitizer 规则怎么从零变成两条。每新增一个 Hook 点都要改 Java 代码、重新打包 Agent、重启应用。上一版的 14 条 Hook 规则直接写在 Java 代码的 `new HookRule(...)` 里，规则少的时候没问题，但继续加下去开发效率会越来越低。所以先把规则从代码里提取出来，放到 `hook-rules.json`，Agent 启动时由 `HookRuleLoader` 读取。以后新增 Hook 点只需要改 JSON，不动 Java 代码。

### 5.1 类加载器隔离与轻量解析

这里有一个类加载器的问题。Agent 由 BootstrapClassLoader（启动类加载器）加载，而 Gson、Jackson 这些第三方 JSON 库在应用 classpath 下，归 AppClassLoader（应用类加载器）管理。双亲委派（Parent Delegation）是单向的——子加载器能访问父加载器的类，父加载器不可访问子加载器的。所以 Agent 里直接 `import com.google.gson.Gson` 会 ClassNotFoundException。理论上可以通过 Thread ContextClassLoader 反射调用 Gson，但那样代码更复杂。本项目的配置文件是扁平的 JSON 对象数组，没有嵌套，用字符串扫描就能取到 key-value：

```java
private static String extractStringValue(String obj, String key) {
    String searchKey = "\"" + key + "\"";
    int keyPos = obj.indexOf(searchKey);
    if (keyPos < 0) return null;
    int colonPos = obj.indexOf(':', keyPos + searchKey.length());
    int valueStart = obj.indexOf('"', colonPos + 1);
    int valueEnd = obj.indexOf('"', valueStart + 1);
    return obj.substring(valueStart + 1, valueEnd);
}
```

几十行代码足够，就没必要绕类加载器去引第三方库。

### 5.2 规则体量与工程化收益

JSON 还声明了 `retransformClasses` 列表——哪些已知类需要在 Agent 启动时立即 retransform（如 `java.lang.Runtime`、`java.lang.Thread`），哪些靠 `canRetransform` 在首次加载时匹配（如 Statement 实现类）。后面新增的 Sink 和 Sanitizer 规则都依赖这个 JSON 配置框架。

基于该框架，当前 `hook-rules.json` 实际承载规则分布如下：HTTP 4 条、SOURCE 12 条、PROPAGATOR 51 条、SINK 86 条、SANITIZER 19 条，另含 THREAD_TRANSFER 1 条，合计 173 条。相比上一版硬编码的 14 条，规则体量扩展一个数量级，新增 Hook 点不再需要改动 Java 代码——规则驱动的工程化收益在此体现。

## 六、能力边界

用 mini-vuln-lab 靶场验证，Agent 检出的 CommandInjection、SqlInjection、SSRF、PathTraversal 等漏洞均能正确上报，参数化查询经 Sanitizer 净化后无误报。检测能力的量化评测（TPR/FPR/FN/FP）见 (五) Benchmark 评测与根因分析。

| 已做到 | 还没做到 |
| :--- | :--- |
| 10 类漏洞、86 条 Sink 规则 | 新漏洞类型需手动加规则 |
| 19 条 Sanitizer 覆盖 SQL/CMDI/XSS | 自定义净化方法不识别 |
| 三元组请求内去重 | 跨请求去重 / 持久化去重 |
| JSON 配置驱动 173 条规则 | YAML / 远程配置中心 |
| 三种 JVM 关系检测模式 | 反射调用（`Method.invoke`）无法拦截 |

Sanitizer 体系覆盖了主流的参数化查询和编码库，但应用自定义的净化方法（如公司内部的 `SecurityUtils.safeSql()`）仍无法自动识别。这类自定义 Sanitizer 需要通过配置扩展，是后续优化方向。

本篇实现的 Path Traversal Sink 命中 `FileInputStream.<init>` 入口检测，能识别基础场景；后续针对 Benchmark 测试集的漏报根因（值级匹配边界、StringBuilder 传播链断裂等）在 (三) 的对象级污点传播部分补全，优化后 PathTraversal TPR 提升至 100%（详见 (五) §6）。
